# Database Standards

This document defines the database design standards for the ExportIQ platform. These standards ensure consistency, maintainability, scalability, and performance across all database objects.

---

# 1. Naming Conventions

## Tables

- Use **plural nouns**
- Use **snake_case**
- Use descriptive names
- Relationship tables should clearly describe the relationship

### Examples

```text
countries
business_verticals
roles
companies
products
certifications

company_role_assignments
company_products
company_certifications
company_data_sources
```

### Avoid

```text
Company
tblCompanies
companyRole
tbl_products
```

---

## Columns

Always use snake_case.

### Good

```text
company_id
product_id
country_id
business_vertical_id
created_at
updated_at
is_active
```

### Avoid

```text
CompanyID
CompanyId
companyID
CreatedDate
```

---

# 2. Primary Keys

Every table must use UUID as its primary key.

```sql
id UUID PRIMARY KEY DEFAULT gen_random_uuid()
```

UUIDs are used internally for all relationships.

---

# 3. Business Identifiers

Every master entity should have a human-readable business identifier.

| Table | Prefix | Example |
|--------|--------|----------|
| companies | CMP | CMP-000001 |
| products | PRD | PRD-000001 |
| roles | ROL | ROL-000001 |
| certifications | CRT | CRT-000001 |
| countries | CTR | CTR-000001 |
| business_verticals | BVT | BVT-000001 |

Business identifiers are intended for users and reports.

UUIDs remain the internal relational keys.

---

# 4. Foreign Keys

Every foreign key column must end with `_id`.

Examples

```text
company_id
product_id
country_id
role_id
business_vertical_id
```

Always use descriptive constraint names.

Example

```sql
CONSTRAINT fk_company_products_company
```

Avoid autogenerated constraint names.

---

# 5. Foreign Key Delete Rules

Use consistent delete behaviour throughout the database.

| Relationship | Delete Rule |
|--------------|-------------|
| Company → Relationship Tables | CASCADE |
| Reference Tables | RESTRICT |

Example

```sql
FOREIGN KEY (company_id)
REFERENCES companies(id)
ON DELETE CASCADE
```

```sql
FOREIGN KEY (product_id)
REFERENCES products(id)
ON DELETE RESTRICT
```

This prevents accidental deletion of master/reference data.

---

# 6. Audit Columns

Every table should contain the following columns.

```sql
created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

is_active BOOLEAN NOT NULL DEFAULT TRUE
```

These columns provide a consistent audit trail across all entities.

---

# 7. Timestamps

Always use timezone-aware timestamps.

```sql
TIMESTAMPTZ
```

Never use

```sql
TIMESTAMP
```

---

# 8. Constraints

All constraints must have meaningful names.

| Type | Format | Example |
|------|--------|---------|
| Primary Key | pk_<table> | pk_companies |
| Foreign Key | fk_<table>_<reference> | fk_company_products_company |
| Unique | uq_<table>_<column> | uq_companies_company_code |
| Check | chk_<table>_<rule> | chk_companies_status |

Avoid autogenerated names whenever possible.

---

# 9. Index Standards

## Do NOT create indexes for

- Primary Keys
- UNIQUE constraints

PostgreSQL automatically creates indexes for both.

---

## Create indexes for

- Foreign keys
- Frequently searched columns
- Frequently joined columns
- Frequently sorted columns

Examples

```text
company_id
product_id
country_id
status
last_verified
```

---

## Avoid indexing

- description
- notes
- large text columns
- boolean columns

Boolean columns should only be indexed when using partial indexes for heavily filtered queries.

---

# 10. Comments

Every table must include documentation.

```sql
COMMENT ON TABLE ...

COMMENT ON COLUMN ...
```

This improves maintainability and allows database tools to display meaningful descriptions.

---

# 11. Transactions

Every migration must use a transaction.

```sql
BEGIN;

...

COMMIT;
```

---

# 12. Migration Standards

Each migration should create only one primary database object.

Good

```text
004_create_companies.sql
```

Bad

```text
create_everything.sql
```

---

# 13. Index Files

Indexes should be created in separate migration files.

Example

```text
004_create_companies.sql

004_companies_indexes.sql
```

Benefits

- Cleaner migrations
- Easier index maintenance
- Faster rebuilds if required

---

# 14. Business Logic

Do not place business logic inside the database.

Avoid

- Workflow logic
- Business calculations
- Complex stored procedures

The database should be responsible for

- Data integrity
- Constraints
- Referential integrity
- Performance

Business rules belong in the application layer.

---

# 15. Soft Deletes

Prefer logical deletion over physical deletion.

```sql
is_active BOOLEAN DEFAULT TRUE
```

Records should generally be deactivated rather than removed.

---

# 16. Status Fields

Use CHECK constraints for controlled status values.

Example

```sql
CHECK (
    status IN (
        'DISCOVERED',
        'IDENTIFIED',
        'ENRICHED',
        'VERIFIED',
        'ACTIVE',
        'DORMANT',
        'ARCHIVED'
    )
)
```

---

# 17. Evidence-First Design

Every business fact that is not part of the Golden Record should be traceable to one or more evidence sources.

Examples

- Company Website
- LinkedIn
- Government Registry
- Trade Directory
- Customs Data
- AI Discovery

This principle is implemented through the `company_data_sources` table.

---

# 18. Golden Record Principle

The `companies` table contains only stable business facts.

Do **not** store the following directly in the company record:

- AI summaries
- Products
- Certifications
- Contacts
- News
- Trade history
- Confidence scores

These belong in their respective domains.

---

# 19. Relationship-Driven Design

Avoid storing multiple boolean flags.

Avoid

```text
is_exporter
is_importer
is_supplier
```

Instead use normalized relationship tables.

```text
roles

company_role_assignments
```

The same principle applies to

- Products
- Certifications
- Contacts
- Data Sources

---

# 20. Standard Migration Naming

Migration files should follow a consistent naming convention.

```text
001_create_countries.sql
002_create_business_verticals.sql
003_create_roles.sql
004_create_companies.sql
005_create_products.sql
006_create_certifications.sql
007_create_company_role_assignments.sql
008_create_company_products.sql
009_create_company_certifications.sql
010_create_company_data_sources.sql
```

---

# 21. Overall Design Principles

The ExportIQ database follows these architectural principles:

- Domain-driven design
- Highly normalized schema
- UUID-based relationships
- Human-readable business identifiers
- Evidence-based data model
- Golden Record architecture
- AI data stored separately from business facts
- Relationship-first modelling
- Scalable and extensible schema
- PostgreSQL best practices
- Keep the database simple; place business logic in the application layer

These principles ensure the database remains maintainable, scalable, and capable of supporting future AI, analytics, and global trade intelligence features.
